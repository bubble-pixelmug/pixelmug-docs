# 运行框架

一个 Bot 应用通常只需要三步：创建实例、注册业务处理器、启动。SDK 将持续接收更新，你不需要自己写轮询循环。

## 两路消息轮询

SDK 内置两路轮询，分别接收用户消息，以及设备上报的事件和 RPC 调用结果；两路更新各自进入独立的队列，按顺序处理。

用户发来文字后，消息先进入 SDK 的用户消息队列。SDK 把原始更新转换成 `ctx`，再依次执行公共中间件和匹配的事件处理器。处理器通过 `ctx.sendText()` 等方法调用云端发送消息。

```js
bot.on('message:text', async (ctx) => {
  await ctx.sendText(`你说的是：${ctx.message.text}`);
});
```

`ctx` 只代表本次事件，里面的 `chat` 是所在对话，`from` 是发送者。处理下一条消息时会创建新的上下文，因此不要用一个全局变量保存“当前用户”。多对话业务应按对话 ID 保存自己的状态。

设备更新使用另一条轮询和队列。这样，文字处理器等待设备响应时，设备队列仍可接收结果并结束这次等待。

## 启动前完成声明

```js
// 按需在这里 registerDevices()、on()、use()。
await bot.start();
```

`start()` 先同步设备声明、默认应用 Bot 设置，再启动轮询。它完成后表示启动步骤结束，不表示已经收到第一条消息。与设备无关的纯消息应用可用 `start({ device: false })`，但启动仍会同步设备声明。

`setCommands()` 会立即请求保存命令菜单，应 `await` 它。设备声明与事件处理器则应在 `start()` 之前准备好。

初始化或 `start()` 本身失败，需要在启动代码中处理；`bot.on('error', ...)` 主要接收运行期间由 SDK 转交的错误。

## 设备调用耗时较长时

用户消息队列按顺序处理消息。如果在处理器中等待设备 RPC 调用完成，后续用户消息也会等待。例如，通过设备 RPC 显示图片时，可能需要等待设备下载、处理并显示图片。SDK 不会为每个对话自动创建独立队列，因此这段等待也会影响其他对话的消息处理。

调用耗时较短时，使用 `await bot.callDevice(...)`，收到设备结果后再回复用户。调用耗时较长时，可以使用 `callDeviceAsync()`，在请求受理后结束当前消息处理，让 Bot 继续处理后续消息；设备返回执行结果后，再通过任务事件通知用户。具体用法见[异步设备调用](./device-rpc#先受理再处理完成事件)。

请求受理不代表设备已经执行完成。异步调用仍需要处理设备返回的错误和等待超时，只是把结果处理移到了任务事件中。

## 停止应用

```js
bot.stop();
bot.clearQueues();
```

`stop()` 停止两路轮询并中止当前轮询请求；`clearQueues()` 清空还未处理的更新。这两个方法不会取消已经执行中的业务处理器，也不会清理应用自己创建的定时器、HTTP 服务或第三方连接。已经发出的设备调用也不能据此视为已取消。

有这些资源时，在应用的退出流程中逐项关闭。若需要等待在途任务完成，由应用记录并等待它们，再结束进程。

## 看懂运行错误

先保留一个简单的错误处理器：

```js
bot.on('error', (ctx) => {
  console.error('[bot]', ctx.error?.name, ctx.error?.message);
});
```

能向用户解释的业务错误，在对应处理器里捕获并回复；其余错误交给统一日志。SDK 的 `debug` 会输出请求详情，可能包含 token，分享日志前应去除凭据。
