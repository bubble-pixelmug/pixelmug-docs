# Audio Service

Audio Service 是 PixelMug S1 Pro 的底层音频服务。PixelMug S1 Lite 版没有音频系统。如果你希望开发声音相关的应用，请确认使用 Pro 产品。通过 `audio_service` 组件使用扬声器、麦克风、Opus 编解码和频谱分析。它也为 [MicroPyxel 的声音合成](/device/micropyxel/audio) 提供输出通道。


## 核心对象及其关系

```python
import audio_service
audio = audio_service.audio
```

`audio` 是单例。`audio.player(...)`、`audio.recorder(...)` 和 `audio.spectrum_analyzer(...)` 创建的是使用同一底层服务的对象，并不是独立的音频设备。

- `Player` 定义格式；`play()` 或 `open_stream()` 返回一次播放的 `PlaySession`。
- `Recorder` 定义读取格式；`start()` 返回一次录音的 `RecordSession`。
- `SpectrumAnalyzer` 配置共享的 PCM 观察缓冲与频谱分析。

同一时刻只管理一个活动播放会话和一个活动录音会话。新的播放采用 `replace`，会替换旧播放；录音需要先结束旧会话再开始。不要通过创建多个对象来实现多路混音。

## 声音经过哪些处理

```text
麦克风 → 16 kHz PCM → AFE 语音前处理 → PCM 帧 → Python 录音
                                           └→ Opus 编码 → Python 录音

Python PCM ───────────────────────→ 播放队列 → 扬声器
Python Opus 包 → 48 kHz 单声道解码 ────┘
MicroPyxel 合成 48 kHz PCM 声音 → 独立队列 ───────┘

输入 PCM / 输出 PCM → 可选观察缓冲 → FFT → Python 频谱快照
```

MicroPyxel 合成声音与普通 PCM／Opus 播放使用不同队列，两路音频处理可以同时运行，但共享同一个音频输出通道，目前不支持两路混音。输出时优先从普通音频队列取数据，普通队列为空时才取 MicroPyxel 队列；已经开始输出的数据块会播放完。普通音频持续占用输出时，MicroPyxel 队列可能填满，使后续合成数据的提交等待空位；普通队列出现空隙时，又可能插入 MicroPyxel 的声音，造成延迟或断续。

**强烈建议应用同一时间只使用一种播放方式。** 播放 PCM／Opus 时，如果 MicroPyxel 仅用于绘图，应使用 `pyxel.init(start_audio=False)`，避免启动不需要的声音合成。

## 内置 AFE：录音的语音前处理

AFE（Audio Front End，音频前端）是在麦克风采集之后、应用读取录音之前的一段处理流程。当前组件使用 ESP-SR 的 AFE，面向人声处理，开启了 VAD 和 NS 模型：

| 能力 | 作用 | 应用如何使用 |
| --- | --- | --- |
| VAD（Voice Activity Detection，语音活动检测） | 判断输入是否处于说话状态；只判断有没有语音，不识别说了什么、是谁在说，也不是唤醒词识别 | 使用 `audio.on("vad", callback)` 注册 "vad" 事件回调。语音状态变化时，在回调中读取 `event["data"]["speaking"]`：`True` 表示检测到说话，`False` 表示变为非说话状态。回调通过持续调用 audio.poll() 触发 |
| NS（Noise Suppression，噪声抑制） | 尽量减少录音中的背景噪声，使人声更清楚；不是保证把所有噪声完全消除 | 当前固件已包含 NSNet2 模型，开始录音后自动进行降噪；应用读取的就是处理后的录音数据，无需额外开启或逐块调用，也没有单独的 NS 事件 |


**VAD 通知不会自动停止录音，也不会自动丢弃非说话期间的数据。** 当前实现把说话状态通知和音频数据输出分开处理：即使 `speaking=False`，应用仍应及时读取录音数据。需要“说完后结束一段录音”时，由应用收到通知后自行决定结束时机。


### 使用时的注意事项
- Opus 的 DTX 则是编码器在安静时减少编码数据量，和 VAD 的状态通知、NS 的降噪处理是不同功能，不能互相替代。
- 当前 Python 接口没有单独开关 VAD / NS、修改 VAD 模式、调整非说话判定时长或切换模型的方法。`audio.configure()` 的音量与输入增益也不改变这些设置。
- VAD 只在检测状态变化时通知，不是每个录音数据块都通知一次；持续安静时没有回调不一定是异常。
- NS 面向语音，可能改变录音的声音细节；不要把经 AFE 输出的录音当作完全未经处理的原始麦克风数据。
- 启动预热、AFE 缓冲、数据分块和 Python 轮询都会影响应用收到数据或通知的时间；60 ms 数据块、100 ms 非说话判定配置都不等于端到端延迟。
- 只关心 VAD 时，也要及时消费录音数据，避免录音队列填满使前面的采集和处理等待。事件回调中保持轻量处理，耗时操作放到应用主循环。

## 支持格式与资源配置

| 项目 | 当前实现 |
| --- | --- |
| 播放 PCM | 输出固定为 **48 kHz**，要求单声道、有符号 16 位、小端、无文件头的数据。**PCM 不会自动重采样**，修改 Player 的 `sample_rate` 也不会改变硬件输出采样率。直接播放其他采样率的 PCM 会改变播放速度和音调：低于 48 kHz 时加快、音调升高，高于 48 kHz 时减慢、音调降低；应先重采样为 48 kHz |
| 录音 PCM | 采样率 16 KHz、单声道、有符号 16 位、小端；当前每帧采集 60 ms 数据交给应用，即 960 个样本 / 1,920 字节 |
| 录音 Opus | 采样率 16 kHz、单声道、每包 60 ms；采用面向人声的编码模式，使用最低编码复杂度以降低 CPU 开销，静音时减少编码数据量（DTX） |
| 播放 Opus | 接收常规单流 Opus 的**完整音频包**，支持单声道和普通双声道（解码时下混为单声道），不支持多声道 multistream。不同源采样率的 Opus（例如由 16 kHz 或 48 kHz 音频编码）均直接解码为 **48 kHz 单声道 PCM**，无需应用自行重采样，不会因源采样率不同而改变播放速度或音调；Player 的 `sample_rate` 必须为 48000（默认值），其他值会报错。每次写入一个完整包，`frame_ms` 应不小于该包的实际总时长；建议使用固定 20／40／60 ms 包。OGG 文件须先拆出 Opus 音频包，不能直接传整个文件或任意文件片段，也不支持 OGG Vorbis |
| 频谱默认值 | 512 点 FFT、16 kHz 频率标尺、50 fps；分析扬声器时须改为 48 kHz |
| PCM 观察缓冲 | 默认每路 64,000 个样本，约 128 KB；开启对应 dump 时按需分配 |

Opus 管线内部保留了“解码采样率与硬件输出采样率不一致时进行重采样”的分支；当前两者均为 48 kHz，因此通常直接输出解码结果，不经过额外重采样。这与原始 PCM 不自动重采样的路径不同。更多包格式与帧长限制见[播放音频](./playback)。

## 后台播放与 Python 轮询

I2S、编解码和 FFT 在后台执行。Python 侧仍需定期调用 `audio.poll()`，以分发事件并更新会话结束状态。只读取 `session.state()` 不会自动推进状态。

主循环中可每 5～20 ms 轮询一次；这是应用组织建议，不是硬性实时保证。使用 `asyncio` 时搭配 `await asyncio.sleep_ms(...)` 主动让出执行。不要在音频回调中进行长时间网络请求或等待同一个会话结束。

程序退出时在 `finally` 中 `audio.deinit()`。如果同时使用 MicroPyxel 合成声音，先停止声音并 `pyxel.destroy()`，最后释放 Audio Service。

## 性能与限制

### 应用需要注意的行为

使用分块读文件、持续写入的方式播放音频，避免一次加载整首歌曲。48 kHz、单声道、16 位 PCM 每秒约占 96,000 字节。

播放队列满时，`session.write(..., wait=True)` 会等待空位；`wait=False` 会抛出 `EAGAIN`，应用应保留当前数据，稍后重试。写入成功只表示数据已入队，不表示已经播放完成。录音也需要及时读取，耗时处理或回调可能使录音管线等待，造成卡顿或延迟。

### 内部队列容量（排查参考）

普通应用无需依赖这些数值；排查卡顿、内存占用和延迟时可参考。

| 内部队列 | 当前容量与含义 |
| --- | --- |
| 普通 PCM 播放队列 | 最多缓存 4 块待播放的 PCM 数据；每块大小由提交的数据决定，因此总字节数和音频时长不固定 |
| MicroPyxel 播放队列 | 最多缓存 4 块待播放的合成 PCM 数据；普通音频持续占用输出时可能积压 |
| Opus 待解码队列 | 最多 40 个完整包；每包 60 ms 时约为 2.4 秒，其他包时长对应的缓存时长不同 |
| 录音 PCM 输出队列 | 缓存经过语音前处理的 PCM 数据，供应用直接读取或交给 Opus 编码器；当前最多缓存 2 个数据块。后续读取或编码跟不上时会使生产管线等待 |
| 录音 Opus 输出队列 | 最多 40 个包；应用读取过慢时会使编码及上游管线等待 |

容量按排队的数据块或包计数，不包含已经取出、正在处理的数据。队列深度不能直接代表总内存占用或端到端延迟，也不能单独用于判断声音已经播放完毕。播放状态排查可结合 [stats() 与队列深度](./controller)，频谱的内存与计算开销见[频谱分析](./spectrum#计算量与刷新限制)。
