# Connect custom BLE centre devices

This page applies to `AUTH_MODE_NONE` open connection mode. PixelMug is BLE Peripheral / GATT Server, custom terminals are active scanning and connecting as Central / GATT Clinic. Bubble App is not required.

This article uses two channel names: the standard message channel corresponds to F150, the high-speed data channel corresponds to F160 (Simple). The UUID and the Simple package header below retains the original name of the protocol.

This paper defines the protocol needed to access the existing application service. It does not open the bottom module of the end of the device, nor does it provide PixelMug with other external interfaces. Different terminals have BLE API and MTU capabilities, which require on-site validation of access.

## Complete example: an ESP32-C3 central device

The warehouse `examples/ble-custom-client` contains `mpy` running on PixelMug, and `custom-client-c3` running on ESS32-C3. C3 scans and connects PixelMug as a BLE central device, sends a number of 0-9 per second and is then automatically disconnected; the cup is then displayed `DISC → CONN → 0…9 → DISC`.

The C3 end provides the ESP-IDF project, introduces `esp-nimble-cpp` through the ESP-IDF component manager, uses the C++ interface it provides to complete initialization, scanning, connection, service discovery and feature writing of BLE, and the developers do not have to directly process the NAP/GATT echo, state of discovery, and attribute handles.

The example is an open mode and F160 high-speed data channel, with a binary number with a Simple package header. The business code is still responsible for the selection of the target device, the construction of the Simple package and the organization of the sending process. The installation, target address and running steps are shown in the project README.

The MPY application interface is still [MPY BLE interface](/en/ble/app/mpy/), with only `AUTH_MODE_NONE` .

## Prepare PixelMug as the peripheral

```python
import time
from maopaoBleApp import BleAppService, AUTH_MODE_NONE

ble = BleAppService("MyApp")

def echo(params, context):
    return {"text": str(params.get("text", ""))}

ble.command("echo", echo, mutates=False)
ble.start(auth_mode=AUTH_MODE_NONE)

try:
    while True:
        ble.poll()
        time.sleep_ms(5)
finally:
    ble.deinit()
```

## Scan and service discovery

From the machine broadcast consists of F150 and F160 services UUID, which are generated by a scanned response name `MPY-<SN><MAC末字节的两位十六进制>`. The name is used only for assistive selection and not as a unique identity. The device needs to be in an application running, broadcast and without other end-ocupancy connections.

The short UUID in the table is expanded using the Bluetooth base UUID, e. g. F150 is `0000f150-0000-1000-8000-00805f9b34fb`.

| Services | Characteristics | Direction & Properties |
| --- | --- | --- |
| F150 | F152 | Host PixelMug, Write / Write without resonance |
| F150 | F151 | PixelMug host,notify |
| F160 | F161 | Host PixelMug, write without resonance |
| F160 | F162 | PixelMug host,notify |

Open mode may still find F140 internal assurance service but do not need to write to it.

## Connection sequence

1. Scan and select PixelMug.
2. Creates a BLE connection, finds service and features.
3. Negotiate sufficiently large MTU when the terminal platform is supported.
4. Subscriptions to F151 (when responding to a request for F150) and F162 (when receiving Simple data).
5. F150 Send hello, save session and max message after successful response.
6. Sends application requests using the current session; restarts connection and handshakes after disconnect.

Only Simple can skip F150 hellos; F162 is not required when sending Simple data to the device. The Simple package depends on open mode release and self-packing, without checking the session.

The current PixelMug links up to one terminal at a time. The terminal is automatically disconnected when you exit; the device follows up the polll and rebroadcasts.

## Standard Message Channel (F150): Message and MTU

Open mode F150 data is the specified UTF-8 JSON. A message corresponds to a feature value written or sent to a notification; no line break, current fusion or application layer automatic sub-contracting. Do not break a JSON into more than one normal writing.

Each message is given `v` as a version of the protocol and `t` as a type of message. Current commonly used values are as follows:

| Fields | Value | Orientation | Meaning |
| --- | --- | --- | --- |
| `v` | `1` | Double | Current protocol version, fixed at 1 |
| `t` | `hello` | Double | Create application sessions and return handshake results |
| `t` | `req` | Host →PixelMug | Send Business Commands |
| `t` | `res` | PixelMug host | Returns command or configuration results |
| `t` | `state` | PixelMug host | Send current application status |
| `t` | `event` | PixelMug host | Send one-time application event |
| `t` | `ping` | Host →PixelMug | Send a heartbeat request |
| `t` | `pong` | PixelMug host | Return heart rate response |
| `t` | `cfg` | Host →PixelMug | Transfer Application Configuration |

The host's request will also indicate the processing level using `p`. The current SDK uses `0` for state snapshots and heartbeats, and `1` for common commands, and `2` for configuration transmissions; the custom host can use a corresponding value for message purposes.

The MTU is M, and the current transfer limit for the device is:

```text
L = min(384, max(16, floor((max(23, M) - 3) / 16) * 16 - 1))
Valid. max_message = min(The requested ceiling for construction, L)
```

This is the conservative ceiling that is currently being applied, and the non-coercive model will not be automatically relaxed. All JSON's UTF-8 bytes are included in the limit.

| Consultation MTU | Transfer limit L |
| --- | --- |
| 23 | 16 bytes |
| 247 | 239 bytes |
| 512 | 384 bytes |

The default MTU = 23 cannot accommodate the application of the hello response, so the "BLE is connected" does not prove that the F150 application protocol works. It is recommended that MTU be negotiated at least 403, bringing the current F150 ceiling to 384 bytes and keeping the paragraphs app id, app version short. MTU = 247 hello may also be too big; if the platform is unable to negotiate enough MTU, small Simple messages can be used to accommodate.

Hello has not previously been obtained max message, and the terminal should pre-empt the hello size according to MTU. When you have received a response, limit the subsequent request by the return value. The tectonic parameter max message cannot break the 384 byte transfer limit.

## Hello and sessions

Hello is the application handshake before the standard message channel starts business communication. It is used to confirm that the current PixelMug is running the required application protocol and obtain the current communication `session`, message size, etc. `session`, device thus groupes message to the current application session and rejects invalid or non-matched reqest; BLE will need to reconnect and send hello. Hello and `session` Do not undertake BLE matching or identification.

Terminal writing F152:

```json
{"v":1,"t":"hello","id":"h1","app":"MyApp","app_version":"1.0"}
```

The device is notified in F151, with only the key fields required to connect to the request shown below, and additional fields such as the list of capabilities omitted:

```json
{"v":1,"t":"hello","id":"h1","ok":true,"session":"0123456789abcdef","app":"MyApp","app_version":"1.0","max_message":384,"config_chunk":128,"rev":0}
```

The terminal must use the actually returned session, without an illustrative value. The device will also give an active notification of the status once after the hello, and the message should be distributed as t.

v must be 1. App should fill in the target identifier and fill in the error will get `application mismatch`; the version does not match `unsupported protocol`. App version is used for the version description and is not currently compatible.

Every new session uses a new hello id. The same hello id sends the same response again when the cache is valid; the new success HI will create a new session. The handshake is created by applying a selection, not by authentication.

## Commands and Responses

Requests:

```json
{"v":1,"t":"req","id":"r1","session":"0123456789abcdef","method":"echo","params":{"text":"hello"},"p":1}
```

Successful response:

```json
{"v":1,"t":"res","id":"r1","session":"0123456789abcdef","ok":true,"result":{"text":"hello"},"rev":0}
```

Failed to respond with ok=false and error instead of result, e. g.:

```json
{"v":1,"t":"res","id":"r1","session":"0123456789abcdef","ok":false,"error":"unknown method","rev":0}
```

Ask id to use a non-empty string, the only one for each new operation. Press id to match the response and check the session. ATT write response only for the result and cannot replace the business response. Standard message channels are also used for status and event notification, which does not wait for business response; both devices on both channels use notey, which cannot be used as confirmation of the end-to-end processing.

Try to keep the same id and content over time. The device caches a limited response and does not commit to double-checking after a session or Cache phase-out.

## Status, event and heartbeat

State means that MPY applies the current set of business values, such as fractions, play-states or sensor readings, and specific fields are defined by the device-end application. `__snapshot` is a state-reading command `BleAppService` that is built in and does not require separate registration for MPY applications; it returns the current state at the time of reading and does not return to historical records.

The host can send a snapshot request after the hello is completed, reconnected or the status version is found:

```json
{"v":1,"t":"req","id":"s1","session":"0123456789abcdef","method":"__snapshot","params":{},"p":0}
```

The device uses the same `id` to return the current status and version:

```json
{"v":1,"t":"res","id":"s1","session":"0123456789abcdef","ok":true,"result":{"state":{"score":10},"rev":1},"rev":1}
```

The device will also proactively send a status notification:

```json
{"v":1,"t":"state","session":"0123456789abcdef","rev":1,"event":"stateChanged","state":{"score":10}}
```

Event notification:

```json
{"v":1,"t":"event","session":"0123456789abcdef","rev":1,"event":"gameOver","data":{"score":10}}
```

The notification does not guarantee that each middleware state will be reached, and the aforementioned snapshot request may be sent when a version gap is detected.

Heart beat requests `{"v":1,"t":"ping","id":"p1","session":"...","ts":123,"p":0}`, responding to tpong and replaying id,ts, carry the current session. The current device pinging processes unvalidated requests session, so pong does not mean that the old session is still valid. The device will not automatically be disconnected simply because there is no ping.

## Configuration messages

Configure messages using t=cfg, with the current session and the only id. The response is uniform as t=res. A recommended string is sent, and one is sent after confirmation.

| op | Extra field | Success |
| --- | --- | --- |
| begin | Name, size, crc32, optional meta | accepted=true, next=0, chunk |
| chunk | offset, data (Base64) | Next;does not match include |
| commit | None | accepted=true, applying=true, crc32, pending |
| abort | None | aborted=true |

It is recommended that each cfg carry a name, but chunk, committee, abort actually works on the only current matter. size, offset is based on original bytes, not Base64 characters. The client moves next to the next of the devices, without losing sight of the retry.

Example:

```json
{"v":1,"t":"cfg","id":"c1","session":"0123456789abcdef","name":"settings","op":"begin","size":2,"crc32":2745614147,"meta":{},"p":2}
```

The above size and crc32 correspond to UTF-8 bytes `{}`, which chunk is:

```json
{"v":1,"t":"cfg","id":"c2","session":"0123456789abcdef","name":"settings","op":"chunk","offset":0,"data":"e30=","p":2}
```

The standard for calculating the whole data CRC32 has no symbol 32-bit integer. The current solid does not enable the end-end of the device CRC32 to verify, and cannot be inferred from the committee response that the data has been independently verified. Commit only indicates that the application is awaited and the final result is confirmed by configApplied/ configError event or application status.

Errors include unknown config, bad config size, no config transfer, config chunk too broad, config overflow, config incomplete, etc. See [Configure Transfer](/en/ble/app/mpy/config) for application processing and transaction limits.

## High-speed data channel (Simple): Subcontracting protocol {#simple-分包协议}

Terminal writes F161 and receives F162 notifications. Each writing or notification happens to be a package with a fixed bytes of 6 bytes:

| Offset | Fields | Value |
| --- | --- | --- |
| 0 | version | 0x01 |
| 1 | flags | 0x00 |
| 2 | data_type | 0x00=RAW; 0x01=UTF-8 text |
| 3 | packet_info | 4-bit total package, 4-bit package serial number |
| 4 | total legth high bytes | Whole message load length, big end |
| 5 | bytes | Without a package header |
| 6 cases | payload | This package load |

The total number of packages is 1 to 8, with serial numbers starting at 0, which must be less than the total number of packages. The whole message is not empty, and the default is no more than 4024 bytes. The package load does not exceed MTU-9.

For example, RAW message `01 20 30` packages sent to:

```text
01 00 00 10 00 03 01 20 30
```

The UTF-8 text `hi` is:

```text
01 00 01 10 00 02 68 69
```

Multipackage message packages must be of the same type, total package number and total length, with a strict increase in serial numbers; all load ciphers must be of the same length as total legth. For example, MTU=23, 20 byte RAW, divided into two bytes of 14+6, with the headers `01 00 00 20 00 14` and `01 00 00 21 00 14` respectively.

The receiving side saves the reorganization by connecting. The package 0 of multiple packages opens a new reorganization; the sequence, type, total number of packages or total length does not match will discard the reorganization. There is no subcontract confirmation, message number or reorganization timeout protocol. The package should be sequentially sent with a message and multiple messages should not be staggered. After failure, re-transmitting should start from the package 0; the single message should not be used as a signal to cancel the old reorganization.

The Simple package headers do not contain application session, message validity, verification or business confirmation fields. When these syntaxes are required, the application is agreed upon and achieved in the load; the F150 command is used when requests and responses are required. Type 1 specifies only that the load is coded using UTF-8, and the text content is formatted in a self-agreement with the application.

## PixelMugBLECENTral

To facilitate the BLE mainframe on embedded development boards such as ETS32, Arduino, and to facilitate the development of desktop or mobile top-up machines, the repository provides a C++ containment category `PixelMugBLECentral`. It binds the connection process described on this page into an application interface, including scanning and connection, MTU consultation, service discovery, F151/F162 subscription, hellos, command response, configuration segment and Simple data subcontracting.

Current achievement at `examples/ble-custom-client-lib/custom-client-c3/BLECentral/`, using ESS-IDF 5.5.x and esp-nimble-cpp 2.5.0. This category can be used directly for this example or as a porter reference: replacement scanning, GATT reading and writing, notification, job synchronization and JSON processing is required when fit for other Arduino BLE libraries, operating systems or on-board BLE API, and the UUID of PixelMug remains unchanged from the application protocol.

The MPY application in the example uses `BleCustomClientLib` as the application identifier, so the host creates objects using the same identifier. `connect()` completes the connection and hello; then the running parameter can be sent down through the configuration interface and the immediate operation triggered by the command:

```cpp
#include <atomic>
#include "PixelMugBLECentral.h"

PixelMugBLECentral mug("BleCustomClientLib");
std::atomic<bool> configApplied{false};

mug.onEvent([&configApplied](const std::string& name,
                             const std::string&,
                             uint32_t) {
    if (name == "configApplied") configApplied = true;
});

if (!mug.begin("My PixelMug Controller") ||
    !mug.connect("AA:BB:CC:DD:EE:FF")) {
    ESP_LOGE("app", "connect failed: %s", mug.lastError().c_str());
    return;
}

const auto config = mug.setConfigJson(
    "circle",
    R"({"color":10,"step":1,"steps":6})"
);
if (!config.ok) {
    ESP_LOGE("app", "config failed: %s", config.error.c_str());
    return;
}

// setConfigJson() Only confirmation of successful submission; Wait MPY Apply Configuration.
for (int elapsed = 0; !configApplied && elapsed < 5000; elapsed += 20) {
    vTaskDelay(pdMS_TO_TICKS(20));
}
if (!configApplied) return;

const auto result = mug.command("nextCircle", "{}");
```

Target addresses should be filled with BLE MACs printed at PixelMug end startup. Classes will only be automatically connected when only one eligible PixelMug in the scan result is omitted. Multiple devices will be found to return errors and avoid being connected to the wrong cup.

`command()`, `requestSnapshot()` and configuration interfaces will wait for the device ' s operational response; `Result.data` Save compact JSON. Status, event and Simple data are received via `onState()`, `onEvent()` and `onSimple()` callbacks. The callback runs in the NimBLE host task, and should return quickly and avoid calling the sync command in the callback. Full device end-to-end configuration, `configApplied` event waiting and GPS9 key control is `mpy/__main__.py` and `custom-client-c3/main/main.cpp`.
