# Device notifications and multi-device routing

The device calls in response to a request; the device notification is generated by the device, for example, a change in the charging state. The receiving notification is `device_notify` and the known event is `parseNotify()` for the device class in device RPC SDK.

## Listen for device notifications

Follow the registered example of S1 `mug` and insert before `start()`:

```js
bot.on('device_notify', (ctx) => {
  const events = mug.parseNotify(ctx.tal?.notify);
  for (const event of events) {
    console.log('Equipment', ctx.from?.id, 'Events', event.name, event.params);
  }
});
```

PixelMug S1 and P1 can be used to detect changes in the state of the device charged by `parseNotify()` for the analysis of the publicly available `CurChargingState` event. This notification is determined by the solid device; registration `device_notify` handler is only for the event that the device has already been reported and does not voluntarily subscribe to or require the device to start reporting.

## Handle charging status changes

The sender of a notice is usually a device, which cannot be considered a user, nor can it be assumed that each notice contains a reversible chat.

A process subscription scheme is shown below: Users send `/watch` in the target chat, Bot query associated devices and remember them. It records many slots in the same chat and allows multiple chats to subscribe to the same device.

```js
const watches = new Map();
const chatKey = (chat) => `${chat.type || 'chat'}:${chat.id}`;

async function refreshWatch(ctx) {
  const devices = await bot.getBoundDevices(ctx);
  watches.set(chatKey(ctx.chat), {
    chat: ctx.chat,
    to: ctx.from,
    deviceIds: new Set(devices.map((device) => device.deviceId)),
  });
  return devices.length;
}

bot.on('message:text', async (ctx) => {
  const text = ctx.message.text.trim();
  if (text === '/watch') {
    const count = await refreshWatch(ctx);
    await ctx.sendText(count ? `Concerns ${count} Associated equipment.` : 'Please contact the device first., Send again /watch.');
  } else if (text === '/unwatch') {
    watches.delete(chatKey(ctx.chat));
    await ctx.sendText('Device notification to stop this conversation.');
  }
});

bot.on('message:bind_device', async (ctx) => {
  if (watches.has(chatKey(ctx.chat))) await refreshWatch(ctx);
});

bot.on('device_notify', async (ctx) => {
  const deviceId = ctx.from?.id;
  if (!deviceId) return;
  const events = mug.parseNotify(ctx.tal?.notify);

  for (const event of events) {
    if (event.name !== 'CurChargingState') continue;
    const value = event.params?.value;
    if (![true, false, 0, 1, '0', '1'].includes(value)) continue;
    const charging = value === true || value === 1 || value === '1';

    for (const [key, watch] of watches) {
      if (!watch.deviceIds.has(deviceId)) continue;
      // Check again., Avoid missing association changes and send them to old conversations.
      const devices = await bot.getBoundDevices({ chat: watch.chat });
      if (watches.get(key) !== watch) continue;
      watch.deviceIds = new Set(devices.map((device) => device.deviceId));
      const bound = devices.find((device) => device.deviceId === deviceId);
      if (!bound) continue;

      await bot.api.sendTextMessage({
        chat: watch.chat,
        to: watch.to,
        mentionOnly: watch.chat.type === 'group',
        text: `${bound.name || 'Water glass.'}${charging ? 'Charging' : 'Charging stopped'}.`,
      });
    }
  }
});
```

Use this group of handlers as an example of a stand-alone notification to replace the business handler with the same name; if combined with already existing `/bind`, `/panel`, it can be assigned to the same text handler or transmitted in [Context & Events](./events) Visible `next()`.

The device is associated, then sent `/watch`, and then changed the device to charge, observing logs and chat notifications. The " focus" here is to apply its own forwarding rules and does not call an additional device subscriber.

## Route events in multi-device applications

The slot is the position in Bot, and `deviceId` is the actual device. When the user replaces the associated device, the slot can change, but `deviceId` changes, so the notification should match the actual device ID and then search for the current slot and display name.

The previous example is appropriate for S1 or for device that uses the same charge events. When different types of device are used in combination, the corresponding device class is saved for each slot, and the corresponding `parseNotify()` is analysed, and it cannot be assumed that all device events are the same.

This is an example of a chat with only one record of concern, the last of which `/watch` replaces the sponsor; if a user within the group is required to subscribe independently, the user ID is also included in the key. After the process is restarted, the memory records are lost, run as long as required, and the list of devices is refreshed when restoration, renewed attention and associated changes are restored. If a change notice for the new associated device is not delivered, it can be updated again `/watch`.
