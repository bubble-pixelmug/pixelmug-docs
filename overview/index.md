# 快速了解

可以把 Bubble 看作一个让“人、应用和设备一起协作”的平台：用户在冒泡 App 中发起交互，Bot 组织应用逻辑，WebApp 提供丰富的操作界面，设备负责在真实世界中执行和反馈。

先用一些例子理解它：你在聊天中对 Bot 说“在我的杯子上画一只小狗”，Bot 找到你关联的 PixelMug，调用设备接口显示一只像素风格的宠物小狗。如果想自己画一个像素表情，可以打开这个 Bot 的 WebApp，用画布创作和编辑，然后让杯子显示。如果想让杯子运行一个互动小游戏，还可以为支持 MPY 容器的产品型号编写设备端程序。

这些能力可以逐步组合。一个只收发消息的 Bot 不需要设备；一个使用固件现成功能的设备应用，也不必编写 MPY。

## 整体逻辑架构

![Bubble App、Bot 与设备的逻辑关系：Bot 和 WebApp 分别连接 TAL，WebApp 还可通过 BLE 与设备交互](/images/bubble-overview.svg)

Bot 和 WebApp 都可以通过 Bubble 提供的 RPC 服务与设备交互；BLE 则为 WebApp 提供手机与附近设备之间的交互通道。

| 组成 | 可以怎样理解 | 主要负责什么 |
| --- | --- | --- |
| 冒泡 App / Bubble App | 用户入口 | 聊天、使用 WebApp、关联设备，管理 bot |
| Bot | 应用的业务中心 | 处理消息与操作、组织业务、关联用户和设备、调用设备并接收反馈 |
| WebApp | 应用的操作界面 | 提供按钮、表单、滑块、画布等丰富交互 |
| TAL | 设备的统一接口 | 把设备能力表达为可调用的方法和可接收的事件 |
| TALID | 一组设备接口的标识 | 说明应用要使用哪一类接口，让应用与具体硬件实现分离 |
| MPY | 在设备上编写应用的运行环境 | 通过 MicroPython 和组件扩展设备行为，适用于 S1 Pro / Lite |

## Bot：把对话、用户与设备联系起来

Bot 是你编写的应用逻辑。用户可以通过私聊或群聊与它交互，Bot 根据消息决定做什么，再把结果回复给用户，或让设备执行动作。

例如，一个提醒 Bot 可以接收“十分钟后提醒我”，到时间后发消息，并让关联的杯子显示提醒。这里的语义理解、计时和提醒规则属于应用逻辑；平台 SDK 提供消息、设备调用等基础能力。是否接入 AI、如何理解自然语言，由开发者决定。

Bot 还把用户和设备的关系带入应用。它先声明需要哪些设备接口，用户再把自己的具体设备关联进去。这样，同一个 Bot 可以服务不同用户，每个人使用自己关联的设备，而应用代码不必写死某个设备的序列号。

当应用进一步组织多人、多设备的交互时，就可以形成 **Device Social Network（设备社交网络）**：人的操作或设备的反馈，可以触发其他参与者或设备的互动。例如，在应用规则和授权范围内，两个冒泡好友可以发送像素表情到彼此的杯子上，或让多个设备参与同一场小游戏。

这是一种围绕用户、Bot 和设备关联关系构建应用的方式。具体谁能控制谁的设备、事件如何传播，仍由关联关系、平台权限和应用规则决定。

## 为什么需要 WebApp？

对话适合表达意图、接收通知和发出简单指令，但不适合所有操作。调节亮度时，拖动滑块比反复输入数字方便；画一幅像素画时，画布比文字描述直接；控制多个设备时，一个面板比一长串消息清楚。

WebApp 就是为这些场景提供的网页界面，用户可以在 Bubble App 中打开并使用它。它与 Bot 一起组成应用：

- 需要业务处理时，WebApp 向 Bot 发请求，由 Bot 返回结果。
- 需要展示变化时，Bot 可以向 WebApp 推送数据。
- 需要操作设备时，WebApp 可以通过冒泡平台提供的设备 RPC 能力，或通过 BLE 与附近设备交互。

例如，用户先在聊天中打开“像素艺术”应用，在 WebApp 中绘制并点击发送，设备显示作品，Bot 再把作品图片发回聊天，便于查看创作记录。这让对话、图形界面和真实设备共同参与一次完整交互。

## TAL：用统一接口描述设备能力

**TAL 是 Things Abstraction Layer，即设备抽象层。** 它把设备的能力描述为应用可以调用的方法和接收的事件，例如开关屏幕、显示内容、读取信息，或上报充电状态。

TAL 的底层设备通信使用 **MQTT RPC**。RPC 可以理解为“请求远处的设备执行一个方法，并返回结果”。开发者通常通过 SDK 组织方法和参数，由平台完成传递，不必为每个应用自行实现底层设备通信。

例如，应用调用“打开屏幕”，只需要表达操作及参数；具体硬件如何驱动显示屏，由设备实现负责。设备执行失败、离线或响应超时，应用仍需要处理相应结果。

TAL 是设备能力的接口约定，MQTT RPC 是底层传输与调用机制，二者处于不同层次。

### TALID 为什么重要？

**TALID 标识一组设备接口。** 例如 `PixelMug`、`PixelMugS1` 对应不同的设备接口集合。SDK 中通常使用字段名 `talId`。

应用声明“我需要支持这个 TALID 的设备”，意味着应用代码依赖这个接口集合。用户再关联符合要求的硬件。应用依赖的是这组接口，而不是某个具体设备的内部实现。这就是软硬件解耦，是应用开发者和设备开发者的约定：硬件可以改进实现，应用继续通过约定的接口使用它。

| 标识 | 回答的问题 |
| --- | --- |
| TALID | 设备提供哪一组能力和事件接口？ |
| deviceId / 序列号 | 是哪一个具体设备？ |

多个硬件型号可以提供同一组接口。比如 PixelMug S1 Pro 和 Lite 是两个硬件型号，但他们的 TALID 相同，因此应用完全兼容

## MPY：让开发者扩展设备本身

TAL 让应用调用固件已经提供的能力，也就是设备厂商提供的能力。对于希望进一步定义设备行为的开发者，**PixelMug S1 Pro 和 S1 Lite 还提供 MicroPython 运行容器**，可以把自己的 MicroPython 应用部署到设备上执行。

设备提供绘图、音频、传感器、按键、BLE 等组件，让开发者组合新的交互。例如，在设备上运行小游戏，根据动作或按键改变画面，或响应手机传来的实时操作。各组件的具体接口与支持条件，会在设备端文档中逐项说明。

这使应用的能力可以扩展到设备内部，不仅依赖固件已有的 TAL 方法。Bot 和 WebApp 负责用户交互与业务协作，MPY 负责设备上的自定义行为。若两端需要交换自定义消息，还需要约定对应的通信方式和消息格式；部署 MPY 并不意味着自动新增一个云端 TAL 方法。

| 设备 | 本文所述 MicroPython 应用容器 |
| --- | --- |
| PixelMug S1 Pro | 支持 |
| PixelMug S1 Lite | 支持 |
| PixelMug P1 | 不支持；通过固件提供的 TAL 接口使用设备能力 |

## PixelMug Studio：调试运行应用的工作台

PixelMug Studio 是开发、运行、调试这些应用的工作台。开发时，它在电脑上启动 Bot、为 WebApp 提供访问地址，并帮助你关联设备、部署 MPY 和查看日志。理解这一点，也就容易看懂项目里的三个部分：

| 项目部分 | 代码运行在哪里 | 什么时候需要 |
| --- | --- | --- |
| `bot/` | 开发电脑或服务器的 Node.js 进程 | 实现消息处理与业务逻辑 |
| `webapp/` | Bubble App 中的网页 | 需要更丰富的图形交互时 |
| `mpy/` | 支持 MPY 容器的设备 | 需要自定义设备程序时 |
